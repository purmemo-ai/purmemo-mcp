# ADR-033 — Purmemo Documentation Repository Architecture

**Date:** 2026-04-28
**Status:** Accepted
**Deciders:** Chris Oladapo

## Context and Problem Statement

Purmemo's documentation has grown to 26 ADRs + ~270 other markdown docs across multiple repos. ADRs land in `purmemo-mcp/docs/adr/` by convention, but ADR-032 explicitly flagged this as a "temporary measure to ensure version control" and called the placement an open question.

The forces:
- ADRs reference code in 5+ repos (purmemo-api, purmemo-mcp, purmemo-frontend, purmemo-amp, purmemo-desktop). Co-locating with any one repo creates an arbitrary winner.
- ADR-022 (Project Intelligence Layer) and ADR-032 (Artifact Replacement Primitives) both push toward derived intelligence over static .md trackers. ADR-032 explicitly says markdown ADRs become snapshots, not source of truth, once `/snapshot` ships.
- 26 ADRs in `purmemo-mcp` is non-trivial inertia. Moving them costs commits + breaks any external links.
- New ADRs should land somewhere predictable today, not in 6 weeks when `/snapshot` ships.

## Decision Drivers

- **D1:** ADR-032 has set direction — the canonical artifact lives in purmemo memory (commitment-shaped), not in a .md file
- **D2:** 26 existing ADRs in `purmemo-mcp/docs/adr/` create real inertia — moving them is reversible but costly
- **D3:** No repo is a natural home for cross-cutting decisions; whatever wins is partly arbitrary
- **D4:** Phase 1 ships in days; Phase 2 ships in 6 weeks — the answer needs to work in both regimes

## Options Considered

**Option 1 — Status quo: keep all docs in `purmemo-mcp/docs/`**
- Pros: Zero migration cost. 26 ADRs already there. Parent repo is the natural umbrella.
- Cons: Conceptually wrong (purmemo-mcp is the *MCP connector*). PR review pollution.

**Option 2 — Dedicated `purmemo-docs` repo**
- Pros: Clean separation. No favoritism. Standard pattern.
- Cons: One more repo. Migration cost. Over-engineering given the planned end state.

**Option 3 — Move docs to `purmemo-api/docs/`**
- Pros: API repo hosts most schema/migration ADRs.
- Cons: Same favoritism problem. Cross-cutting ADRs out of place.

**Option 4 — ADRs are commitments in purmemo memory; .md files are renders**
- Pros: Aligned with ADR-032 end state. Self-dogfooding. Searchable via `/api/v1/commitments/?type=ADR`. Cross-AI accessible.
- Cons: `/snapshot` and `/render` not shipped yet. Cloning the repo doesn't surface them in a file tree.

## Decision Outcome

**Chosen option: Hybrid 4 + 1 — primary source is purmemo memory; `purmemo-mcp/docs/adr/` is the rendered cache.**

**Rules:**
1. All new ADRs from ADR-033 onward are written via `/decide` → `/commit`, producing a `commitment_type='ADR'` memory in production. That memory is the canonical source.
2. A rendered `.md` copy is committed to `purmemo-mcp/docs/adr/` for discoverability when cloning the repo, external linking, and machine-readable static archive. The `.md` is a render artifact, not source of truth.
3. No migration of existing 26 ADRs. They remain in place as historical artifacts. After `/render` ships, batch-import old ADRs as commitments at leisure.
4. PRDs and specs follow the same rule — memory primary, optional rendered copy.

**Rationale:**
- D1 honored: source of truth is the memory; .md is a render
- D2 honored: zero migration cost; existing ADRs stay put
- D3 partly accepted: rendered cache stays in purmemo-mcp by inertia, but is no longer load-bearing
- D4 honored: works today (commit + manually copy markdown), works after `/render` ships (automatic regeneration)

## Consequences

**Positive:**
- ADR-033 is the first ADR shipped through the new pipeline — strongest possible dogfood
- No repo politics; the memory is the canonical home
- Composes cleanly with the four-primitive architecture
- Discoverable both ways: filesystem and query

**Negative:**
- Two places to update during the gap before `/render` automates the cache
- Risk of drift if memory and .md updated separately — mitigation: treat .md as read-only output once `/render` ships

**Risks:**
- Risk: developers continue writing .md ADRs directly. Mitigation: ADR-032 line 219 success metric (≥80% via /prd or /decide) tracks exactly this.
- Risk: external links to old ADR paths break if we ever consolidate. Mitigation: keep purmemo-mcp/docs/adr/ paths stable.

## Implementation Plan

1. Save this ADR via POST /api/v1/memories/ with commitment_type='ADR'
2. Write the rendered .md to `purmemo-mcp/docs/adr/ADR-033-documentation-repository-architecture.md`
3. Commit + push to purmemo-mcp parent repo
4. After /render ships: automate the rendered-cache regeneration
